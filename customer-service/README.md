
# Customer Service

Customer Service is a Spring Boot microservice responsible for managing customer information within the FinTech Core platform.

It provides APIs for registering customers, retrieving customer information, and validating customer data.

The service is designed as a standalone microservice so that customer-related business rules and data remain isolated from other FinTech Core services.

## Responsibilities

The Customer Service is responsible for:

- Registering customers
- Validating customer information
- Storing customer information
- Retrieving customer information
- Maintaining customer lifecycle information
- Enforcing customer-related business rules

The service does **not** own authentication or payment processing.

Those responsibilities belong to other services within FinTech Core.

## Domain Model

The primary domain entity is `Customer`.

A customer currently contains:

| Field            | Description                                    |
| ---------------- | ---------------------------------------------- |
| `id`             | System-generated UUID identifying the customer |
| `customerNumber` | Optional business/customer identifier          |
| `firstName`      | Customer's first name                          |
| `lastName`       | Customer's last name                           |
| `email`          | Customer's email address                       |
| `phoneNumber`    | Customer's phone number                        |
| `status`         | Customer status                                |
| `kycStatus`      | Customer KYC status                            |
| `createdAt`      | Timestamp when the customer was created        |
| `updatedAt`      | Timestamp when the customer was last updated   |

### Customer ID vs Customer Number

The service generates the technical `id` using a UUID.

```text
id
└── Generated by Customer Service
    └── Used as the system's technical identifier
```

`customerNumber` is treated differently.

It represents a business-facing customer identifier and may be provided by the business or upstream system.

It is therefore not generated automatically by the Customer Service.

The field is currently optional to allow the service to support different business requirements without unnecessarily coupling the implementation to a specific customer-number generation strategy.

For example:

```json
{
  "firstName": "Ryan",
  "lastName": "Bondoc",
  "email": "ryan@example.com",
  "status": "ACTIVE"
}
```

A customer can therefore be created without a customer number.

If a business unit later requires customer numbers, the API can accept one:

```json
{
  "firstName": "Ryan",
  "lastName": "Bondoc",
  "email": "ryan@example.com",
  "status": "ACTIVE",
  "customerNumber": "CUST-10001"
}
```

This separation allows the technical identifier and business identifier to evolve independently.

## API

### Register Customer

```http
POST /customers
```

Registers a new customer.

#### Request

```json
{
  "firstName": "Ryan",
  "lastName": "Bondoc",
  "email": "ryan@example.com",
  "status": "ACTIVE"
}
```

#### Response

```json
{
  "id": "bee5da62-25aa-4aeb-8678-e922c3549c30",
  "firstName": "Ryan",
  "lastName": "Bondoc",
  "status": "ACTIVE",
  "email": "ryan@example.com",
  "customerNumber": null
}
```

The UUID is generated by the service.

### Get Customer

```http
GET /customers/{id}
```

Retrieves a customer using the system-generated UUID.

Example:

```bash
curl http://localhost:8082/customers/bee5da62-25aa-4aeb-8678-e922c3549c30
```

## Validation

Customer information is validated before invalid data is persisted.

Current validation includes:

### Email

The email address must have a valid email format.

Example of an invalid request:

```json
{
  "firstName": "Ryan",
  "lastName": "Bondoc",
  "email": "not-an-email",
  "status": "ACTIVE"
}
```

The service returns:

```http
HTTP/1.1 400 Bad Request
```

The invalid customer is not persisted.

### Customer Number

When supplied, the customer number must satisfy the configured length requirements and must be unique.

The customer number is currently configured to allow:

```text
5-20 characters
```

## User Stories

The current implementation supports the following customer-management user stories.

### CUS-001 — Register Customer

> As a user, I want to register my personal information so that I can create a FinTech Core account.

The service supports registration through:

```http
POST /customers
```

The customer is persisted and assigned a system-generated UUID.

### CUS-002 — Validate Customer Information

> As a user, I want my personal information validated so that invalid data cannot enter the system.

Validation is implemented using Jakarta Bean Validation and persistence-level validation.

Examples include:

* Email format validation
* Customer number length validation
* Customer number uniqueness

## Design Principles

Customer Service follows several principles important to financial systems:

* **Separation of responsibilities** — customer management is isolated from authentication, transactions, and payments.
* **System-generated technical identifiers** — UUIDs provide stable technical identifiers without depending on business numbering schemes.
* **Business identifiers remain flexible** — customer numbers can be supplied by an upstream business system when required.
* **Validation before persistence** — invalid customer information should not enter the database.
* **Service ownership of customer data** — other services should consume customer information through the Customer Service API rather than directly accessing its database.
* **Independent evolution** — the service can evolve independently from other FinTech Core microservices.
